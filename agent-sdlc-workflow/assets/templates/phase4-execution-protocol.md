# 模板4：执行监控与回流协议

> 阶段 4 的操作规程。模式：**auto = 低干预、高可见**，不是无人值守。
> agent 每完成一个任务/phase 按本协议产出证据；人按 §4 的节奏巡检。

## 1. 任务执行循环（agent 侧）

```
领任务卡 → 开机三读（宪章 → 任务卡 → NOTES.md）
→ TDD：失败测试 → 实现 → 重构
→ 自验证：全量 lint/typecheck/test/e2e
→ 自证：证据落盘（/plans/logs/<task-id>/）
→ 更新 NOTES.md → 按 DAG 领下一任务
```

## 2. Checkpoint 报告（每任务必产，每 phase 汇总）

```markdown
## Checkpoint: <task-id> @ <时间>
- 结果：[完成 / 部分完成 / 阻塞]
- 门控证据：测试 __/__ 通过；e2e 截图：<路径>
- 偏差报告：[无 / 有 → 见 §3]
- 实际耗时 vs 预算：__ vs __（超 2 倍需说明原因）
- NOTES.md 已更新：是
```

## 3. 升级策略（Stop-and-Ask）

agent 遇到以下任一情况**必须停止并请求人类介入**，禁止"灵活发挥"：

| 触发条件 | 升级内容 |
|----------|----------|
| spec 歧义或与现实冲突 | 冲突点 + 两种以上解释/方案 + 建议 |
| 同一门控连续失败 ≥ 3 次 | 失败日志 + 已尝试方案 + 假设 |
| 前置假设被证伪（模板1 §1） | 被证伪的假设 + 影响面分析 |
| 需越权（新依赖/白名单外文件/破坏性操作） | 具体请求 + 理由 |
| 验收标准本身有误 | 走 spec 回流（宪章 §6），不擅自"修正意图" |

## 4. 人类巡检节奏

| 节点 | 动作 |
|------|------|
| 每个 phase 退出门控 | 审 checkpoint 汇总 + 抽查证据 + 放行/打回 |
| 每次升级事件 | 决策 + 必要时修订 spec/ADR |
| 每日/固定节奏 | 扫 NOTES.md 与偏差记录，关注漂移信号 |
| 任意时刻 | 可随时抽查 `/plans/logs/` 的审计轨迹 |

## 5. 上下文卫生（长程执行防漂移）

- 任务边界即上下文边界：新任务新开上下文，靠开机三读冷启动，不依赖对话记忆
- 上下文逼近上限时优先**任务内 compaction**：保留决策与未决问题，丢弃冗余工具输出
- `NOTES.md` 是跨上下文的唯一记忆通道——重要发现**必须落盘**，留在对话里等于丢失
- 发现 agent 开始重复犯错/遗忘约定 → 检查 AGENTS.md 是否缺失该约定，补文档而非重复口头纠正

## 6. Spec 回流台账

执行期所有 spec 变更登记于此（与宪章 §6 配套）：

| 日期 | 任务 | 冲突/错误描述 | 处置（spec 更新/ADR/驳回） | 批准人 |
|------|------|----------------|----------------------------|--------|

> 本台账是阶段 5 复盘的核心输入：高密度的回流记录 = 阶段 1 的需求/建模质量信号。

## 7. 失败与回滚

- 每个 phase 完成后打 git tag（`phase-P__-done`），作为回滚点
- phase 门控打回时：回滚到上一 tag 或原地修复，由人决策并记录
- 任何回滚事件记入 §6 台账（回滚是前期阶段质量问题的最强信号）
