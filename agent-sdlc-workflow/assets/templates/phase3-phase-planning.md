# 模板 3：Phase 与任务计划

> 保存为 `plans/<milestone>.md`。优先端到端可验证增量，不按技术层横切。

单任务 fast-track 可直接在对话或现有 issue 中写目标、AC 和验证命令，不创建本文件。

Project Mode 由 Agent 根据 spec、原型和环境闭环先提交完整草案；人与 Agent 在这一阶段讨论范围和取舍，不让人手工从空白 Todo 开始拆分。

## Phase

| Phase | 可验证增量 | 退出门控 |
|---|---|---|
| P0 | 最薄主路径 | __ |

优先处理高不确定、高影响或难回退部分，让错误尽早暴露。

## 任务卡

```markdown
### T1：<可验证目标>
- AC：AC-__
- 依赖：无 / T__
- 影响区域：__（仅用于估算与并发协调，不是文件权限白名单）
- 验证：__
- Review/ADR：无 / __
- 完成信号：__
```

任务大小以模型能在一次专注执行中理解、实现并验证为准，不设置固定文件数或时长。执行发现漏列文件时直接修改，在 checkpoint 概括影响即可。

## 依赖与并行

- DAG 无环；标出真正的前置依赖。
- 只避免实际写冲突；共享只读文件不妨碍并行。
- migration、公共 schema、lock 等共享写点由一个 Agent 串行处理。
- 某任务阻塞时继续其他依赖已满足的任务。

## Copilot → Auto 交接

Agent 一次性汇总：Phase 增量、完整 Todo、关键路径、风险、各阶段退出门控和预计人工 gate，并声明交接状态：

- `Plan-ready`：规格和计划足以审阅，但环境反馈闭环尚未实测，或用户本次只要求规划包。
- `Auto-ready`：环境命令与工程 canary 已实测，计划可由 Agent 独立验证和推进。

只有 `Auto-ready` 计划经人确认关键目标与取舍后，才成为阶段 4 的执行 goal；之后不为普通任务或 Phase 逐项请求批准。`Plan-ready` 应列出升级到 `Auto-ready` 的剩余条件。

## 退出门控

- [ ] 每条 AC 被任务覆盖，每个任务有验证方式
- [ ] 每个 Phase 都产生可验证增量
- [ ] 依赖与共享写点清楚
- [ ] 各 Phase 的退出门控可由阶段 2 的闭环验证
- [ ] 已明确 `Plan-ready` / `Auto-ready`；若移交执行，人已集中确认目标与关键取舍，不做逐文件签字
