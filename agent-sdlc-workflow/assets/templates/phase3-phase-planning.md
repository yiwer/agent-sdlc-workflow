# 模板3：Phase 划分与任务规划

> 阶段 3 的产出物，存为 `/plans/<milestone>.md`。交给 agent 执行的就是本文件。
> 核心认知：**任务切分质量直接决定长程执行的成败**——粒度决定上下文窗口利用率、漂移概率和纠偏成本。

## 1. Phase 划分原则

- 每个 phase 产出**可独立验证的增量**（能跑、能测、能演示），不是"写了一半的层"
- 优先竖切（端到端薄片）而非横切（先全部模型、再全部接口、再全部 UI）
- 高风险/高不确定性项前置（早失败、早回流）
- 推荐结构：P0 骨架贯通（最薄的端到端）→ P1..n 逐层加肉 → 收尾加固

| Phase | 目标 | 产出增量 | 退出门控 |
|-------|------|----------|----------|
| P0 | 端到端骨架 | 主路径可跑通（丑但通） | G0：主路径 e2e 通过 |
| P1 | | | |

## 2. 任务卡（Task Card）格式

> 每张任务卡 = agent 的一次专注执行单元。上下文预算超限的任务必须再拆。

```
### Task <id>：<一句话目标>
- 所属 Phase：P__
- 验收标准（引用 spec）：AC-__、AC-__
- 上下文预算：预计涉及文件 ≤ __ 个；预估执行时长 ≤ __ 分钟（以干跑基线校准）
- 涉及文件/目录（白名单）：__
- 依赖任务：<id>（无依赖标 0）
- 并行性：[可并行 / 串行区：__]（串行区：DB migration、lock 文件、共享配置）
- 退出门控：
  - [ ] 新增/修改测试通过，且覆盖 AC-__
  - [ ] 全量 lint + typecheck + 测试套件绿
  - [ ] 证据落盘（测试报告 / e2e 截图）
- 完成信号：一句话说明"怎么一眼看出做完了"
```

## 3. 依赖图（DAG）

```
P0: T1 → T2 → T3
P1: T4（依赖 T2）、T5（依赖 T2，可与 T4 并行）、T6（依赖 T3）
...
并行冲突检查：T4/T5 无文件白名单交集 ✓
```

- [ ] 所有任务构成 DAG（无环）
- [ ] 标记了关键路径（决定总工期的链）
- [ ] 可并行任务之间的文件白名单两两无交集

## 4. 上下文交接协议

任务之间不靠"记忆"传状态，靠落盘资产：
- 每个任务完成后：更新 `NOTES.md`（进度打勾 + 一句话结果 + 遗留坑）
- 跨任务的设计决定 → ADR；spec 变更 → 走宪章 §6 回流流程
- 新任务启动时 agent 的"开机三读"：宪章/AGENTS.md → 本任务卡 → NOTES.md 近况

## 5. 规模校验（防"任务过大"）

- [ ] 每张任务卡的上下文预算 ≤ 一次专注上下文可容纳量（经验：涉及文件 ≤ 5–8 个）
- [ ] 任何任务预估时长 > 干跑基线的 3 倍 → 必须再拆
- [ ] 无法拆小的任务（如复杂接口设计）显式标记为"copilot 任务"，**不放行到 auto 阶段**

---
### 阶段 3 退出门控
- [ ] 每条 AC 至少被一张任务卡引用；每张任务卡至少引用一条 AC（双向可追溯）
- [ ] DAG 无环、并行无冲突、关键路径已标注
- [ ] 每个 phase 的退出门控可由阶段 2 的自动化回路测量
- [ ] 人审阅并签字确认任务清单（这是 auto 阶段前最后一个人工关卡）
