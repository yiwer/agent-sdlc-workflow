# Agent 时代软件工程工作流（六阶段模型）

> 原始框架：准备 → 环境搭建 → 任务规划 → 长程执行（四阶段，前三阶段 copilot、末阶段 auto）。
> 本模板包在其基础上扩展为六阶段，并补齐三个结构性缺口：**宪章层（阶段 0）**、**执行中的 spec 回流机制（阶段 4）**、**验收与沉淀飞轮（阶段 5）**。

## 总览

| 阶段 | 名称 | 模式 | 核心产出物 | 对应模板 |
|------|------|------|------------|----------|
| 0 | 宪章（Constitution） | copilot | 不可变原则、质量门槛、agent 自主边界 | `模板0-项目宪章.md` |
| 1 | 需求与建模 | copilot | 需求规格、五维模型、可执行验收标准（EARS）、原型 | `模板1-需求与五维建模.md` |
| 2 | 环境与闭环 | copilot | 自动化质量回路、agent 基础设施、部署流水线 | `模板2-环境与闭环门控清单.md` |
| 3 | 规划与切分 | copilot | phase 划分、任务 DAG、上下文预算、退出门控 | `模板3-Phase任务规划.md` |
| 4 | 长程执行 | auto（低干预、高可见） | 代码、checkpoint 证据、偏差与回流记录 | `模板4-执行监控与回流协议.md` |
| 5 | 验收与沉淀 | copilot | 一致性审计、验收报告、宪章/模板更新 | `模板5-验收与复盘.md` |

## 三条核心设计原则

1. **Spec 即源码，代码是 spec 的编译产物。** 需求不是写给读者看的文档，而是 agent 执行、验证、汇报所依据的契约。验收标准必须可执行（EARS / Given-When-Then），否则阶段 4 的门控无法自动化。
2. **agent 的自主性上限 = 反馈回路的自动化程度。** 阶段 2 的目标不是"装工具"，而是让 agent 能自己 lint、自己跑测试、自己部署、自己截图自证——形成无需人类介入的验证闭环。
3. **auto ≠ unattended（自动 ≠ 无人值守）。** 阶段 4 是"低干预、高可见"：checkpoint 协议、升级策略（何时必须停下来问人）、spec 回流（执行中发现前期假设错误时的变更控制）。

## 与业界实践的对照（2026 年中）

- 本模型与 GitHub Spec Kit 的 `constitution → specify → clarify → plan → analyze → tasks → implement` 六步流程高度同构，可以互操作：阶段 0 ≈ constitution，阶段 1 ≈ specify/clarify，阶段 3 ≈ plan/tasks，阶段 4 ≈ implement。
- 长程执行的上下文管理（compaction、结构化笔记 NOTES.md、子代理分工）参考 Anthropic 的 context engineering 与 long-running harness 实践。
- 任务分级（fast-track）：并非所有变更都需要全套六阶段。小规模变更走 `宪章 → 简版 spec → plan → implement`，但仍必须留 spec 记录——这是保持 spec 驱动纪律不崩塌的关键。

## 使用方式

1. 项目启动时复制模板 0，与人协同填写，作为仓库根目录的 `CONSTITUTION.md`（或并入 `AGENTS.md`）。
2. 按阶段 1→2→3 顺序推进，每阶段用模板末尾的门控清单做退出检查；门控未过不得进入下一阶段。
3. 阶段 4 把 `模板3` 的任务清单交给 agent，用 `模板4` 的协议监控执行。
4. 阶段 5 完成复盘后，把沉淀项回写宪章——下一个项目的阶段 0 从更新后的宪章开始，形成飞轮。
