## 2. 一致性审计（spec 与代码是否还是一回事）

- [ ] spec 描述的行为与实现逐一核对（可让独立 agent 做交叉审计）

- [ ] ADR 与实际架构决策一致，无"做了但没记"的决策
- [ ] 审计出的漂移全部处置：改代码对齐 spec，或改 spec 追认现实（需人批准）

## 3. 过程复盘

### 3.1 数字回顾
| 指标 | 值 | 信号解读 |
|------|----|----------|
| 升级事件次数（模板4 §3） | | 高 → 阶段 1 规格质量不足 |
| spec 回流次数（模板4 §6） | | 高 → 需求挖掘/建模遗漏多 |
| 门控打回次数 | | 高 → 任务切分或环境回路问题 |
| 任务平均实际/预算耗时比 | | 偏离 1 → 阶段 3 估算基线失真 |
| 人工介入总时长 | | 衡量 auto 的真实成色 |

### 3.2 三问
1. **哪些前期假设错了？**（回溯模板1 §1 的假设清单——被证伪的假设当时为何没识别出风险？）
2. **哪些门控没拦住问题？**（问题穿透到了哪一层才被发现？漏检的门控如何加强？）
3. **哪些人工介入本可避免？**（缺的回路、缺的文档、缺的护栏分别是什么？）
