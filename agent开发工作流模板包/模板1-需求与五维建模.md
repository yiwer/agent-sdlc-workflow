# 模板1：需求规格与五维建模

> 阶段 1 的产出物。填充后存为 `/specs/<feature>.md`。
> 关键要求：§4 的验收标准必须**可执行**——阶段 4 的每一条 playwright 测试都应能追溯到这里的编号。

## 1. 需求定位

| 项 | 内容 |
|----|------|
| 一句话价值主张 | 谁在什么场景下获得什么价值 |
| 目标用户与角色 | |
| 成功度量 | 怎么算做成了（可观测指标，不是"用户体验好"） |
| **非目标（Out of Scope）** | 明确不做什么。比目标更重要——这是 agent 防 scope creep 的护栏 |
| 前置假设 | 本需求成立依赖的假设清单（阶段 4 回流的主要触发源） |

## 2. 边界条件确认

逐项回答，写"无"也要显式写：

- [ ] 输入边界：最大/最小/非法输入的行为定义
- [ ] 空态与零数据：列表为空、首次使用、权限不足时的呈现
- [ ] 并发与幂等：重复提交、并发编辑、网络重试的语义
- [ ] 失败模式：下游不可用、超时、部分失败的降级行为
- [ ] 权限矩阵：每个角色对每个行为可/不可（一张表）
- [ ] 性能预算：关键路径的延迟/吞吐上限

## 4. 可执行验收标准（EARS + 场景）

用 EARS 句式：**WHEN <条件>，THE SYSTEM SHALL <行为>**（可选 IF/WHILE 变体）。
每条编号，供任务卡和 e2e 测试引用。

| 编号 | 验收标准 | 关联规则/行为 | 验证方式（e2e/单元/人工） |
|------|----------|----------------|---------------------------|
| AC-1 | WHEN 用户提交空表单，THE SYSTEM SHALL 拒绝提交并逐字段标注错误 | R-3 | e2e |
| AC-2 | … | | |

关键场景（Given/When/Then，覆盖主路径 + 至少 2 条异常路径）：
```
Scenario: ___
  Given ___
  When  ___
  Then  ___
```
